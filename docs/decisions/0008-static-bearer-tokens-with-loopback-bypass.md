# 0008. Authenticate network surfaces with static bearer tokens and a loopback bypass

Date: 2026-10-04
Status: accepted

## Context

`yrm web` and `yrm serve --http` put the event log (the user's mail) and the ability to record human-origin facts behind a port. Until now neither had authentication; the dashboard warned and the HTTP transport did not exist. Anyone who could reach the port could read everything and write facts that outrank models. See [SECURITY-MODEL.md](../SECURITY-MODEL.md).

The solo demo must stay zero-config, CI and containers need secrets from the environment, and agents need their own identities so `origin.by` says who wrote a fact. 0.1 has one tenant per install and no user directory.

## Decision

Static bearer tokens, a loopback bypass, and a signed session cookie for the browser, in a new `@yrm/ext-auth` package that `@yrm/ext-web` and `@yrm/ext-mcp` import.

- Tokens come from `settings.auth.tokens` (`{ name, token | tokenEnv, principal, scopes }`) or from `yrm auth token create`, which stores only a SHA-256 in kv `auth/tokens/<name>`. Both are checked on every request in constant time; kv is re-read so a revoke takes effect at once.
- Scopes are `read` and `write`. Write routes and write tools refuse without `write`, even when an agent passes `confirm: true`.
- The principal comes from the token, never from tool arguments: it becomes `ToolContext.principal` for MCP and `by` for dashboard writes.
- Requests from a loopback peer pass without a token unless `settings.auth.allowLoopback` is false. Servers refuse to bind a non-loopback address while no token exists.
- The dashboard's `/login` exchanges a token for an `HttpOnly; SameSite=Strict` cookie: token name and expiry, HMAC-signed with a per-install secret in kv `auth/secret`.
- MCP over HTTP uses the SDK's web-standard Streamable HTTP transport in stateless JSON mode, one server per request, so each request runs with exactly its token's principal and scopes.

## Consequences

Solo use is unchanged. Exposing either server takes one command. Each agent can have its own principal and a read-only token. Revocation is immediate.

Tokens do not expire, so a leaked token lasts until someone revokes it. Behind a reverse proxy on the same host every caller looks like loopback, and the operator must turn the bypass off. Scopes are tenant-wide. There is no TLS; that is the proxy's job. Stateless MCP means no server-initiated messages or resumable streams, which YRM does not use today.

## Alternatives considered

- **OAuth 2.1 as the MCP authorization spec describes:** right for hosted, multi-user deployments, far too much machinery for one person on a laptop; tokens can be swapped for it later behind the same `Grant`.
- **A single per-install token generated by `yrm init`:** simpler, but every client would share one identity, and `origin.by` would stop meaning anything.
- **No loopback bypass:** safer behind proxies, but it breaks the zero-config demo and every existing stdio-to-HTTP migration.
- **Unix socket only:** strong local isolation, but browsers and most MCP hosts cannot use it.
